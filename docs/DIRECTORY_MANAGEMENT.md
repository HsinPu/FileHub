# 目錄管理與多目錄授權

## 範圍

保留單根目錄帳號授權；新增多目錄個別授權、管理員目錄狀態與權限範本。第三輪完成帳號及基本檔案操作，第四輪整合批次操作、分享與撤權。

## 部署設定

預設 `compose.yaml` 使用 Docker `files` 資料卷，容器根目錄為 `/files`。不掛入外部資料夾，不需要建立 `srv/`；多目錄 Linux 範例已移除。

基本部署請見 [Docker 說明](DOCKER.md)。預設未宣告多目錄清單，管理頁只顯示總根目錄，一般帳號可使用單一根目錄模式。

多目錄授權功能仍保留。進階使用時，可自行在 Compose environment 加入 `FILES_DIRECTORIES` JSON 清單，並先在資料卷建立對應第一層目錄。僅在 `.env` 填寫不會生效，因為基本 Compose 未轉送此設定。

每筆宣告包含固定 `id`、`name` 與第一層相對 `path`，最多 100 筆；`root` 是保留識別碼。宣告不會建立目錄或授予帳號權限。Windows 本機啟動仍使用 `FILES_ROOT` 設定。

## 管理畫面

管理員在「設定 → 目錄管理」查看根目錄及已宣告目錄。狀態包含可讀、目錄不存在、不是資料夾、無法存取；可手動重新檢查。只有管理員 API 會回傳容器根路徑。

「寫入權限檢查」僅使用作業系統權限提示，不建立測試檔，不能證明實際寫入成功；ACL、唯讀掛載、配額、剩餘空間仍可能阻止操作。裝置編號比較也無法完整辨識每一種 bind mount。

帳號編輯沿用既有資料夾選擇器，顯示目錄檢查結果。新增唯讀、一般作業、完整作業範本；選取範本取代現有勾選，分享另行授權。既有帳號不會自動套用範本。後端儲存時仍驗證目錄及權限。

帳號可選「單一根目錄」或「多目錄授權」。舊帳號預設保留單一根目錄，不會自動增加目錄或操作權限。

多目錄設定步驟：

1. 在「目錄管理」確認部署清單的目錄可讀取。
2. 進入「帳號管理 → 編輯帳號」，將「存取模式」改為「多目錄授權」。
3. 新增目錄授權，逐一選擇目錄及權限範本；分享須另外勾選。
4. 儲存後，此帳號既有登入會撤銷。重新登入後根頁為「所有目錄」，只列出授權的第一層資料夾。

範例：

| 目錄 | 帳號授權 | 登入後行為 |
| --- | --- | --- |
| shared | 一般作業 | 可瀏覽、下載、上傳、建立、修改／搬移 |
| reports | 唯讀 | 可瀏覽、預覽、下載；可複製到其他可寫目錄 |
| documents | 未授權 | 根頁不顯示，直接呼叫 API 也會拒絕 |

「所有目錄」只是導覽頁，不能直接上傳、建立資料夾或貼上。檔案頁名稱採用實際資料夾名稱；部署清單的 name 用於管理頁辨識。多目錄 path 包含第一層資料夾（例如 reports/2026/report.pdf）；單目錄帳號仍使用相對於自己根目錄的 path。

每個目錄必須有瀏覽權限，分享需同時具備讀取權限。應用程式授權不會更改 Linux 權限；實際操作還必須符合容器 UID/GID、ACL、唯讀掛載與磁碟限制。此版未增加群組、逐檔案 ACL 或網頁掛載功能。

部署目錄的 id 或對應 path 改變後，不會把舊授權自動套到新位置；修改顯示名稱也會保留原授權。若要授權新位置，請先移除舊的目錄授權並儲存，再重新新增目錄授權並儲存。失效目錄不會阻擋停用帳號；重新啟用時必須先移除或修正失效授權。相同 path 下更換主機來源不會由此機制自動辨認，因此仍需部署者管理掛載與資料來源。

## 操作授權

| 操作 | 多目錄授權條件 |
| --- | --- |
| 瀏覽 | 目前目錄 browse |
| 預覽、下載、ZIP | 每個來源 read |
| 上傳、建立資料夾 | 目的目錄 upload |
| 重新命名 | 來源目錄 modify |
| 複製 | 來源 read，目的 upload |
| 搬移 | 來源 modify，目的 modify + upload |
| 移至垃圾桶 | 來源 delete |
| 還原 | 本人刪除的項目、原路徑仍在授權範圍，目的 upload |
| 分享 | 來源 read + share；公開下載時再次檢查 |

管理員不受一般帳號目錄授權限制。舊單目錄帳號的原本搬移條件維持 modify。

帳號設定變更會更新授權版本、撤銷登入及使舊分享／任務失效。多目錄任務還會比對建立時的授權與部署對應；上傳與批次作業在提交檔案前再次檢查。ZIP 完成後下載、分享已驗證過的 Cookie 也會重新檢查。已完成的部分保留，不自動回復；已傳送到用戶端的內容無法收回。資料夾上傳重送不會沿用已失效的目的映射。

## 操作限制與驗證

目前垃圾桶集中於根目錄 `.files-app-trash`；跨檔案系統的移至垃圾桶與還原會被拒絕。多掛載可用於瀏覽，不代表所有寫入、搬移與垃圾桶操作都可用。不同裝置會在目錄管理顯示限制；同裝置仍須實測 bind mount 行為。

首次正式部署前，使用測試檔逐一驗證：瀏覽、上傳、下載、同目錄重新命名、同目錄搬移、跨目錄複製、移至垃圾桶、還原及重啟後狀態。不要用正式檔案測試跨掛載搬移。已宣告的部署根目錄與系統可辨識的掛載點，後端禁止重新命名、搬移或移至垃圾桶；目錄內的檔案仍依帳號權限操作。

備份須同時涵蓋 database/config volumes、根目錄垃圾桶與所有主機來源目錄；先停止服務確保一致。不要使用 `down -v`。

API：`GET /api/v1/admin/directories` 回傳清單；`GET /api/v1/admin/directory-status?path=...` 檢查選定相對目錄。兩者皆為管理員限定、唯讀並使用既有路徑安全檢查。

## 升級與回退

資料庫版本 7 新增 scope_mode、directory_grants 與稽核明細。啟動時自動遷移，保留舊 root、permissions、帳號角色及版本；可重複啟動。帳號建立／更新稽核記錄包含授權前後值，不包含密碼。

正式更新前須備份 SQLite、config 金鑰、集中垃圾桶及所有掛載來源，並停止服務確保一致。若要回退程式，應一併還原更新前的資料庫；不要只把映像降版。此輪只使用隔離資料庫驗證遷移，未操作正式資料。

第三輪與第四輪的計畫與驗證紀錄見 [MULTI_DIRECTORY_PLAN.md](MULTI_DIRECTORY_PLAN.md)。依需求不執行第五輪 Linux 完整驗收及部署。
