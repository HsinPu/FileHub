# 第三輪與第四輪實作規劃

## 目標與界線

依序完成第三輪，再完成第四輪；只修改與驗證本機程式。不執行第五輪 Linux 完整驗收及部署，不新增群組／逐檔案 ACL，不改寫 Docker 掛載，不搬移既有實體檔案。

## 第三輪：多目錄授權

1. 新增版本 7 遷移：AccountAccess 增加 scope_mode（single 預設，multiple 可選），新增帳號目錄授權表。舊帳號 root、permissions、角色完全保留；不推算或擴張舊帳號授權。
2. 每個授權記錄 directory_id、授權時的目錄路徑與 permissions，限定第一輪已宣告的目錄；目錄 ID 或對應路徑變更即拒絕沿用舊授權，避免改掛載設定後靜默擴權。
3. 帳號管理明確選擇單目錄／多目錄模式。多目錄逐列選擇目錄及權限範本，重複目錄、缺少瀏覽權限、分享缺少讀取等均由後端驗證。
4. 多目錄使用者以總根目錄作為導覽頁，僅列出已授權的第一層目錄；導覽根不能上傳、建立或貼上。進入後依該目錄的權限顯示操作。一般單目錄使用者原入口不變。
5. 保留既有 path API 契約：單目錄 path 相對於帳號 root；多目錄 path 為包含已授權第一層路徑的相對路徑。目錄固定 ID 用於授權，部署路徑快照用於一致性驗證。此階段不強制重寫既有任務／分享路徑。
6. 所有 ScopedFiles 操作每次 resolve 檢查路徑授權及版本。清單不能洩漏未授權檔名。第三輪中尚未整合的批次任務及分享對多目錄模式先拒絕，不能留下只改畫面的授權缺口。
7. 第三輪閘門：遷移可重跑、舊帳號限制不變、多目錄瀏覽／下載／上傳／改名權限正確、管理畫面及窄螢幕驗證通過後，才開始第四輪。

## 第四輪：完整操作與撤權

1. 統一以實際來源／目的路徑授權。複製需來源 read、目的 upload；搬移需來源 modify、目的 modify+upload（單目錄舊語意保留）；刪除需來源 delete；還原需項目歸屬、來源範圍與目的 upload；ZIP 每一來源需 read。
2. 任務提交、開始、逐項與提交檔案前檢查授權版本。多目錄任務另保存授權目錄配置快照；配置變更時拒絕舊任務及重送。已完成部分如實記錄，不自動反向搬移。
3. 分享建立與公開開啟／下載都檢查來源 read+share、擁有者狀態及版本。撤權後舊分享 Cookie 也不能重新取得檔案。
4. ZIP 完成後下載重新驗證全部來源，撤權後不再提供既有成品。
5. 資料夾上傳重送包含版本及目錄配置，重送也重新檢查目的授權；串流上傳在提交前重新 resolve。
6. 垃圾桶沿用目前實體格式與資料庫，依多目錄授權過濾列表和還原目的地；不在這輪移動既有垃圾桶。跨檔案系統垃圾桶／還原／搬移仍明確拒絕，不以複製後刪除暗中替代。
7. 前端複製、剪下、貼上、操作對話框及垃圾桶目的地採路徑別能力；後端仍為最終授權者。
8. 第四輪閘門：混合來源、不同目的權限、分享撤權、ZIP 撤權、排隊／執行中撤權、重送、垃圾桶還原及既有單目錄回歸通過。

## 相容、驗收與進度

- 維持原登入撤銷機制：帳號更新增加 version 並撤銷該帳號既有 sessions。
- 只在隔離 SQLite 與暫存檔案測試，不開啟正式資料庫執行遷移。
- 更新前須備份 DB、config 金鑰及所有資料目錄；程式回退需搭配更新前 DB，不能只降版程式。
- Python：pytest、修改範圍 Ruff；前端：TypeScript/Vite、Playwright 及實際截圖檢視。
- 保留第一輪尚未提交的修改，不做 Git 提交、推送或 server 部署。

進度：第三輪已通過 12 項後端測試、5 項瀏覽器案例（修正測試選取後重跑通過）、TypeScript/Vite 與三種寬度截圖檢查。第四輪整合與驗證已完成。

## 審查問題修正（2026-09-15）

- P1：既有授權路徑只從已儲存記錄保留，一般資料更新不重新綁定目前部署路徑。變更目錄位置須先移除舊授權並儲存，再新增授權；改權限或重新啟用時也不能靜默改綁。
- P2：更新帳號時先取得現有授權，再驗證變更；停用可保留失效的既有目錄授權，仍增加版本並撤銷登入。重新啟用會重新檢查目錄與權限。
- 驗證：原先 3 個回歸案例先失敗、修正後通過；追加目錄移除、改指向、實體目錄不存在等情境，相關帳號／授權／遷移測試合計 28 項通過。兩個原始重啟重現情境也已重新執行通過；Ruff 與差異空白檢查通過。
- 此次修改限後端、測試與文件，未修改前端、執行部署或提交 Git。修正已由實作者驗證，尚未經獨立再次審查。
